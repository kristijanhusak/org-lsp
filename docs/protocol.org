#+title: Protocol
#+options: ^:{} toc:2

org-lsp uses standard LSP. This page says what it offers and lists the
names an editor integration deals with: options, commands, the manifest,
the agenda document and the semantic tokens.

* Capabilities

The requests the server answers:

- ~textDocument/didOpen~, ~didChange~, ~didSave~, ~didClose~ :: Incremental
  sync. A save rebuilds an open agenda.
- ~textDocument/willSaveWaitUntil~ :: With ~org-crypt-use-before-save-magic~
  in Emacs's configuration, the edit that encrypts the entries tagged
  ~crypt~ (~org-encrypt-entries~), through Emacs. Emacs is asked only for
  files with a ~:crypt:~ tag until it has said it has the magic. Else none.
- ~textDocument/semanticTokens/full~, ~/range~ :: For Org files and the
  agenda. See [[#semantic-tokens][Semantic tokens]]. No deltas.
- ~textDocument/foldingRange~ :: Subtrees, drawers, blocks, LaTeX
  environments and multi-line list items. Whole lines only. A subtree takes
  the blank lines before the next headline along, as Emacs hides them; see
  ~org_cycle_separator_lines~. Headlines deeper than ~org_cycle_max_level~
  have no fold of their own, nor list items with
  ~org_cycle_include_plain_lists~ ~false~.
- ~textDocument/documentSymbol~ :: The outline of headlines. Hierarchical
  when the client supports it, flat otherwise.
- ~textDocument/codeAction~ :: The commands that apply at the cursor. See
  [[#commands][Commands]].
- ~workspace/executeCommand~ :: Every command. See [[#commands][Commands]].
- ~textDocument/definition~ :: In the agenda: from a line to its entry. In
  an Org file: where a link or a footnote leads; on a citation key, its
  entry in the bibliography (~org-cite-basic-goto~: the start of its line,
  or for a CSL-JSON file its opening brace; the start of the file when Org
  finds no entry there), elsewhere in a citation the entries of all its
  keys.
- ~textDocument/hover~ :: In the agenda: the line's entry, its headline and
  its text up to the next heading, each drawer folded to its first line as
  Emacs shows a folded drawer (~:PROPERTIES:...~), as Org in a fenced block
  of Markdown. In an Org file, over a citation key, its entry as Org's help
  echo shows it (~oc-basic~'s ~plain~ style:
  ~Knuth. The {\TeX}book, Addison-Wesley, 1984.~), or for a key no
  bibliography file has, ~Suggestions:~ and the keys at most two edits away
  from it. Elsewhere none. An editor that shows the entry in an Org buffer
  of its own can have it highlighted by opening that buffer as an Org
  document with a URI that is no file (Neovim: ~org-preview:/1~); such a
  document is no file of an agenda built from the open files.
- ~org-lsp/startupFolds~ :: The folds a file opens with closed, as
  ~org-cycle-set-startup-visibility~ leaves it: ~org_startup_folded~ and the
  file's ~#+STARTUP:~ (~overview~, ~content~, ~show2levels~ …,
  ~showeverything~), then each subtree's ~VISIBILITY~ property, archived
  subtrees, blocks with ~hideblocks~ (~org_cycle_hide_block_startup~) and
  drawers (~org_cycle_hide_drawer_startup~). ~{ "folds": [FoldingRange…] }~,
  innermost first, each one of ~textDocument/foldingRange~'s. Params:
  ~{ "textDocument" }~. The editors close them when a file opens.
- ~org-lsp/ellipsis~ :: What a closed fold shows after its first line
  (~org_ellipsis~, ~...~ unless it is set), a string, for an editor that
  draws closed folds itself (~foldtext~). Params: none. The ~initialize~
  result has the same as ~capabilities.experimental.orgEllipsis~.
- ~org-lsp/journal~ :: Where org-journal's files are, for an editor to
  open those without an extension as Org files: ~{ "directory" }~, the
  absolute path of ~org_journal_dir~ ending in ~/~, or null when
  ~org_journal_enabled~ is off. Params: none. The ~initialize~ result has
  the same as ~capabilities.experimental.orgJournal~.
- ~org-lsp/preview~ :: The same text of an agenda line's entry with its
  semantic tokens, for an editor that shows it in a popup of its own:
  ~{ "text", "data" }~ (~data~ as in ~SemanticTokens~), or null. Params:
  ~TextDocumentPositionParams~.
- ~org-lsp/faces~ :: The faces of particular TODO keywords, priorities
  and tags (~org_todo_keyword_faces~, ~org_priority_faces~,
  ~org_tag_faces~), for an editor to apply over the semantic tokens of the
  keyword (~todoKeyword~) or the priority (~priority~), and, in Org files
  only, over the name of each tag of a headline's ~tag~ token (~:a:b:~,
  the colons left as they are):
  ~{ "todo": { KEYWORD: face }, "priority": { LETTER: face }, "tag": { TAG: face } }~, each face
  ~{ "foreground", "background", "bold", "italic", "underline", "strikethrough" }~,
  those set. The same is in the initialize result as
  ~capabilities.experimental.orgFaces~. Params: none.
- ~textDocument/completion~ :: In a headline: TODO keywords for the first
  word after the stars, and the file's tags after a ~:~ in the headline's
  tags (~pcomplete~). ~:~ triggers it. After ~@~ in a citation (~[cite:@…~),
  the keys of the bibliography, each with its authors, year and title as
  Org's completion table has them (~detail~).
- ~workspace/textDocumentContent~ :: The text of the agenda. See
  [[#the-agenda-document][The agenda document]].
- ~textDocument/onTypeFormatting~ :: After a line break: ~org-indent-line~
  on the new line (Org's ~RET~), following ~org_adapt_indentation~. No edit
  when the line is indented right, or when Org leaves such a line as it is
  (headlines, the first line of a list item, the code of a source block).
- ~textDocument/rangeFormatting~ :: ~org-indent-region~ over the lines of
  the range (text, drawers and blocks re-indented, node properties aligned
  as ~org-property-format~ has them), then, as ~textDocument/formatting~
  does for the whole file, every table with a line in the range aligned
  whole (~org-table-align~) and the tags of the headlines in the range put
  in their column (~org-align-tags~). A range that ends at the start of a
  line leaves that line out. One edit per changed line.

The server sends ~textDocument/publishDiagnostics~ for the citation keys of
a document that no file of its bibliography has (~oc-basic~ shows them with
the ~error~ face): severity Information, as an Org file is text and nothing
in it is an error or a warning, /Unknown citation key: @key/, with the keys
at most two edits away (~org-cite-basic--close-keys~) in the message and in
~data.citationKeys~, from which ~textDocument/codeAction~ offers quick fixes
(/Replace with @key/). The bibliography is the files of the document's
~#+BIBLIOGRAPHY:~ lines (relative to it) and of ~org_cite_global_bibliography~:
BibTeX files (~.bib~, read with the ~biblatex~ dialect, and ~.bibtex~), parsed
as ~bibtex.el~ parses them (~@String~ expansion, ~#~, field names in lower
case), and CSL-JSON files (~.json~). A file Org cannot read (malformed, a
duplicate key) adds nothing; Emacs then fails for the whole bibliography.

The server sends these requests to the client:

- ~workspace/applyEdit~ :: A command changes an Org file.
- ~window/showDocument~ :: To show the agenda, a capture buffer, or the file
  of an agenda entry. The editors open the agenda and capture buffers in a
  window of their own (a split by default), and an entry's file where the
  agenda was. With ~"orgOtherWindow": true~ (not LSP's;
  ~org.agenda.goto.other~, TAB in the agenda) the editors of this project
  show the file in another window: one that shows it, else an empty one,
  else a new one. The org-roam buffer (a file whose name starts with the
  manifest's ~roamBuffer.prefix~) comes with ~takeFocus: false~: the
  editors show it beside the file it is for, the cursor staying there.
- ~workspace/textDocumentContent/refresh~ :: The agenda has new text.

And these notifications:

- ~org-lsp/columns~ :: What column view (~org-columns~, through Emacs) shows
  on a document, for the editor to draw over its headlines:
  ~{ "uri", "version", "header", "columns": [{ "key", "title", "width" }], "lines": [[line, text, [value…]]] }~,
  each line a headline's, with the text it shows and its values; ~lines~
  null when it goes off. Sent when it is turned on (~org.columns~), after
  each of its commands and each change of the document. Its commands
  (~org.columns.*~, in the ~columns~ scope of the manifest) take the column
  picked, from 0, as ~column~ in their argument.
- ~org-lsp/timer~ :: ~{ "seconds", "countdown", "paused" }~ when the
  relative timer or a countdown of Org in Emacs starts, pauses, goes on or
  changes, and null when it stops (unless ~org-timer-display~ is nil): its
  value then, which the editor counts on each second (down for a countdown)
  unless it is paused, to show as ~<0:05:23>~, as Emacs's mode line does.
- ~org-lsp/save~ :: ~{ "uris": [uri…] }~: with ~auto_save~, the files a
  command changed other than the one it was run in (an entry's file changed
  from the agenda, the target of a capture or a refile), once the editor has
  applied the change. The editor saves those with changes.
- ~org-lsp/virtualIndent~ :: For a client that announces
  ~experimental.orgVirtualIndent: true~: how the lines of a file with
  ~org-indent-mode~ (~org_startup_indented~, ~#+STARTUP: indent~) or hidden
  leading stars (~org_hide_leading_stars~, ~#+STARTUP: hidestars~) show.
  ~{ "uri", "version", "lines" }~, each line
  ~[line, prefix, wrap, hiddenStars]~: the columns shown before the line
  (~line-prefix~), before the lines it wraps into (~wrap-prefix~), and how
  many of a headline's leading stars show as blanks. Lines with nothing to
  show are left out. Sent after the file opens and after every change while
  it shows so, and once with no lines when it stops. Only for the version
  given.
- ~org-lsp/display~ :: For a client that announces
  ~experimental.orgDisplay: true~: what shows in place of hidden text, the
  entities and sub- and superscripts of ~org_pretty_entities~ (~α~, ~x²~)
  the bullets of ~org_bullets_mode~, and the shrunk table columns
  (~org-table-shrink~). ~{ "uri", "version", "items" }~, each item ~[line,
  character, endLine, endCharacter, shown, look]~: the range hidden, the
  text shown in its place, and, for a bullet, the token whose colors it
  takes, as a selector of the manifest's ~highlights~ (~stars.level1~,
  ~bullet~, ~checkbox.checked~); left out when there is none. Sent after every change
  while there are some, and once with no items when there are none. Only
  for the version given. A client that does not announce it gets the same
  as inlay hints.
- ~org-lsp/images~ :: For a client that announces
  ~experimental.orgImages: true~ (or sets the option ~images~): the images
  of the LaTeX fragments ~org.latex.preview~ asked for, once Emacs has made
  them, in the form the preview commands answer with (see
  ~org.link.preview~), ~kind~ ~latex~.
- ~org-lsp/lineHighlights~ :: For a client that announces
  ~experimental.orgLineHighlights: true~ (or sets the option
  ~line_highlights~): the lines of the agenda to highlight from edge to
  edge, as Emacs's overlays cover them, past the end of their text.
  ~{ "uri", "lines" }~, each line ~{ "line", "highlight" }~; ~highlight~
  names the token type whose look it takes (~agendaClocking~: the entry the
  clock runs on, ~org-agenda-clocking~). Sent once the client shows the
  agenda's current text, after each new text it shows, and when the lines
  change (clocking in or out), with no lines when none is highlighted. The
  text of those lines also has the token type, for clients that show only
  tokens.
- ~org-lsp/folds~ :: ~{ "uri", "open": [FoldingRange…], "close": [FoldingRange…] }~:
  after a journal command has shown a file (~window/showDocument~), the
  headlines' folds to open, then those to close (innermost first), as
  org-journal leaves them (~org_journal_hide_entries_p~). Each is one of
  ~textDocument/foldingRange~'s.
- ~org-lsp/viewChanged~ :: With the option ~view_changed~: ~{ "uri" }~, the
  file of the agenda or of the date prompt has been written anew, for the
  client to read it again.
- ~org-lsp/clock~ :: The clock that runs, for a status line: ~null~ when
  none does, or ~{ "heading", "minutes", "effort", "text", "uri", "line" }~,
  the entry's headline, the minutes clocked on it so far (since
  ~LAST_REPEAT~ if it has one), its effort in minutes or ~null~, the text of
  Emacs's mode line (~[0:25/1:00] (Write the report)~), and where the entry
  is. Sent when the clock starts or stops, and when the server starts with a
  clock running in the files. The editor counts the minutes on from there.
  When the time clocked reaches the entry's effort, the server shows
  ~Task ‘Write the report’ should be finished by now. (1:00)~
  (~org-clock-notify-once-if-expired~), once for each clock; ~effortText~ is
  the effort as written.

And from the client, these notifications (also taken as requests, for
clients that send none of their own):

- ~org-lsp/agendaCursor~ :: ~{ "textDocument", "position" }~: the line of
  the agenda the cursor is on, each time it changes. In follow mode
  (~org.agenda.follow~) the server answers with ~window/showDocument~ for
  the entry of that line, ~takeFocus: false~ and ~orgOtherWindow: true~: the
  client shows it in another window and keeps the cursor in the agenda.
  Sent as a request, with ~width~ the columns of the editor's echo area if
  it has one, it is answered with ~{ "echo": "work.org/Projects" }~: the
  outline path of the line's entry (~org-agenda-show-outline-path~), cut
  to fit as Emacs cuts it, for the client to show as Emacs's
  ~org-unlogged-message~ does (the echo area, the status bar), or ~null~.
- ~org-lsp/cursor~ :: ~{ "textDocument", "position" }~: the line of an Org
  file the cursor is on, each time it changes, while the editor shows the
  persistent org-roam buffer. When the cursor is in another node of
  org-roam's files, the server writes the buffer for it
  (~org-roam-buffer-persistent-redisplay~).
- ~org-lsp/setClock~ :: ~{ "today", "now" }~: for tests, moves the fixed
  clock of a server started with the ~clock~ option; ignored otherwise.
- ~org-lsp/agendaWidth~ :: ~{ "width": N }~: how many columns of text the
  window that shows the agenda has, when it opens and whenever its size
  changes. With ~org_agenda_tags_column~ ~"auto"~ the tags end at that
  column, and the server builds the agenda again when it changes; without it
  they end at column 80.

*Position encoding.* The server picks UTF-8 if the client offers it, then
UTF-32, and falls back to UTF-16.

*Line endings.* ~\n~, ~\r\n~ and a lone ~\r~ all end a line for positions.
A file whose every line ends with ~\r\n~ keeps its endings in the edits
of formatting and the table commands.

*Not followed.* The server does not register for
~workspace/didChangeWorkspaceFolders~ or ~workspace/didChangeWatchedFiles~:
a folder added after ~initialize~ is read only when the server starts
again, and a file renamed outside the editor keeps its old name for the
clock's history and the agenda's marks until then.

* Options
:PROPERTIES:
:CUSTOM_ID: options
:END:

Passed as ~initializationOptions~, on top of the shared configuration file
the server reads itself (=~/.config/org-lsp/config.toml= or ~config.json~;
see [[file:configuration.org][configuration.org]]): an object such as ~org_agenda_prefix_format~ is
merged key by key, anything else replaces the file's. The names are Org's
variable names with ~_~ for ~-~ (~org_agenda_files~; ~org-agenda-files~ is
read too), and the values Org's, as JSON; options of the server's own have
plain names (~auto_save~). Defaults are Org's. The names options had before
are read and named in a message; unknown options are ignored, and named in
a message. ~org-lsp settings~ prints them as JSON, and the list below is
written from it by ~scripts/generate-docs.mjs~; [[file:configuration.org::#every-option-at-its-default][configuration.org]] shows the
same defaults as a configuration file.

Each option with its type, its default and what it means:

# BEGIN generated: options

- ~config_file~ :: false, or a path, the shared file, =~/.config/org-lsp/config.toml= or ~config.json~. The shared configuration file, whose options this editor's go on top of: ~false~ for none, or the path of another file (JSON if it ends in ~.json~, else TOML). Unset, it is ~$ORG_LSP_CONFIG~, else ~config.toml~ or ~config.json~ in ~$XDG_CONFIG_HOME/org-lsp~ (=~/.config/org-lsp=; ~%APPDATA%\org-lsp~ on Windows).
- ~org_agenda_files~ :: string[], ~[]~. Files, directories and glob patterns (~*~, ~?~, ~**~) the agenda is built from. =~/= is the home directory, and a directory stands for the Org files directly in it. When empty, the agenda is built from the Org files under the workspace folders (hidden directories, ~node_modules~ and ~target~ left out), or else from the Org files that are open. (~org-agenda-files~)
- ~org_agenda_file_regexp~ :: string, the ~.org~ files whose names do not start with a dot. Which files of a directory in ~org_agenda_files~ are agenda files: an Emacs regular expression their names match (Org's is ~\\~[^.].*\\.org\\'`). (~org-agenda-file-regexp~)
- ~org_agenda_skip_unavailable_files~ :: boolean, ~false~. Leave out the files of ~org_agenda_files~ that are not there. With ~false~, opening an agenda view asks about each: ~r~ removes it from the list until the server starts again, anything else aborts. (~org-agenda-skip-unavailable-files~)
- ~org_todo_keywords~ :: string[] | string[][], ~["TODO", "|", "DONE"]~. The TODO sequence, written like Org's ~#+TODO:~ line. ~|~ separates the states that count as done; without it the last keyword is the only done state. ~TODO(t)~ gives a keyword a key for fast selection, and ~WAIT(w@/!)~ makes it log a note (~@~) or the time (~!~) on entering and leaving it. Several sequences go in a list of lists, ~[["TODO", "|", "DONE"], ["REPORT", "|", "FIXED"]]~; cycling stays in the sequence of the entry, and ~C-S-<right>~ switches to the next. A list that starts with ~type~ is a type sequence (~#+TYP_TODO:~): each of its keywords goes straight to done. A file's own ~#+TODO:~ lines take precedence. (~org-todo-keywords~)
- ~org_todo_keyword_faces~ :: { [keyword]: string }, ~{  }~. Faces for particular TODO keywords: a color, ~{ "WAIT": "orange" }~, or attributes written as Org writes them, ~{ "CANCELLED": ":foreground gray :slant italic :strike-through t" }~ (~:foreground~, ~:background~, ~:weight bold~, ~:slant italic~, ~:underline t~, ~:strike-through t~). Shown in Org files and in the agenda by Neovim, Vim and VS Code. (~org-todo-keyword-faces~)
- ~org_priority_faces~ :: { [priority]: string }, ~{  }~. Faces for particular priorities, by their letter, written as in ~org_todo_keyword_faces~: ~{ "A": ":foreground red :weight bold" }~. (~org-priority-faces~)
- ~org_tag_faces~ :: { [tag]: string }, ~{  }~. Faces for particular tags of headlines, written as in ~org_todo_keyword_faces~: ~{ "work": "orange" }~. Shown in Org files (not the agenda, as in Emacs) by Neovim, Vim and VS Code. (~org-tag-faces~)
- ~org_log_done~ :: false, "time", "note", ~false~. Write ~CLOSED:~ with the time when an entry is done, and with ~note~ ask for a note too. A file's ~#+STARTUP:~ words ~logdone~, ~lognotedone~ and ~nologdone~ change it there; an entry's ~LOGGING~ property (inherited) says what its state changes log instead: those words, ~logrepeat~ and its relatives, and keywords with what they log (~WAIT(@/!)~), or ~nil~ for nothing. (~org-log-done~)
- ~org_log_repeat~ :: false, "time", "note", ~"time"~. Record when a repeating entry is done and moves to its next date. ~#+STARTUP:~ ~logrepeat~, ~lognoterepeat~ and ~nologrepeat~ change it in a file, and the ~LOGGING~ property in an entry. (~org-log-repeat~)
- ~org_M_RET_may_split_line~ :: boolean, object, ~true~. Inserting a heading, an item or a table row (M-RET) in the middle of a line splits it, the rest going to the new one; ~false~: it goes in after the line. One by context: ~{ "headline": false, "item": true, "table": true }~, ~default~ for those not named. (~org-M-RET-may-split-line~)
- ~org_blank_before_new_entry~ :: object, ~auto~ for both. Whether a new heading (~heading~) and a new item (~plain_list_item~) get an empty line before them: ~true~, ~false~, or ~"auto"~, as the headings or items around them have. (~org-blank-before-new-entry~)
- ~org_insert_heading_respect_content~ :: boolean, ~false~. M-RET and M-S-RET outside lists put the new heading after the subtree, as C-RET does. (~org-insert-heading-respect-content~)
- ~org_special_ctrl_a_e~ :: false, true, "reversed", [C-a, C-e], ~false~. How C-a and C-e (~org.beginning.of.line~, ~org.end.of.line~) move on a headline or an item: ~true~ to the start of the headline's title, after the stars, TODO keyword and priority, or after the item's bullet and check-box, and to the end of the title, before the tags; the same key again to the line's own start or end. ~reversed~ goes to the line's start or end first, and to those places on the same key right after. A pair, as ~[true, false]~, sets C-a and C-e apart. With ~false~ the key keeps the editor's own meaning. (~org-special-ctrl-a/e~)
- ~org_sparse_tree_open_archived_trees~ :: boolean, ~false~. A sparse tree (~C-c /~, and a link's ~/regexp/~) shows its matches in archived subtrees (tagged ~ARCHIVE~); with ~false~ those subtrees stay folded under their headline. (~org-sparse-tree-open-archived-trees~)
- ~org_occur_case_fold_search~ :: true, false, "smart", ~true~. Whether a sparse tree (~C-c /~, and a link's ~/regexp/~) ignores case; ~"smart"~ ignores it unless what is searched for has an upper-case letter. (~org-occur-case-fold-search~)
- ~org_sparse_tree_default_date_type~ :: null, "all", "active", "inactive", "scheduled", "deadline", "closed", ~null~. The timestamps the date sparse trees (~C-c /~ ~b~, ~a~, ~D~) look at first: ~null~ for scheduled and deadline dates, or one kind; ~c~ in the menu turns to the next kind. (~org-sparse-tree-default-date-type~)
- ~org_yank_adjusted_subtrees~ :: boolean, ~false~. C-y (~org.yank~, Emacs keys) of one or more subtrees at the start of a line, or after the stars of an otherwise empty headline, pastes them as ~org.paste.subtree~ does: at the level of the headlines around them. Anything else is the editor's own paste. (~org-yank-adjusted-subtrees~)
- ~org_allow_promoting_top_level_subtree~ :: boolean, ~false~. Promoting a headline of level 1 makes it a comment line: ~# ~ in place of ~* ~, its children a level up with a subtree's promotion. With ~false~ it is an error. (~org-allow-promoting-top-level-subtree~)
- ~org_odd_levels_only~ :: boolean, ~false~. Only odd levels: ~*~, ~***~, ~*****~, each counted as the next level. Promoting and demoting go two stars at a time, and a headline is colored and matched (~LEVEL~) by the level it counts as. ~#+STARTUP: odd~ and ~oddeven~ set it for a file. (~org-odd-levels-only~)
- ~org_treat_S_cursor_todo_selection_as_state_change~ :: boolean, ~true~. ~S-<left>~ and ~S-<right>~ on a headline change its TODO state as any change does: logged, and blocked by its dependencies. Off, they change it with nothing logged and nothing in the way. (~org-treat-S-cursor-todo-selection-as-state-change~)
- ~org_treat_insert_todo_heading_as_state_change~ :: boolean, ~false~. The keyword of a heading ~org.insert.todo.heading~ (M-S-RET) makes is set as a TODO change: logged as the keyword says (a note wanted is a time only), with its tag triggers. (~org-treat-insert-todo-heading-as-state-change~)
- ~org_edit_timestamp_down_means_later~ :: boolean, ~false~. ~S-<down>~ makes a timestamp later and ~S-<up>~ earlier, the other way round from Org's default. (~org-edit-timestamp-down-means-later~)
- ~org_priority_enable_commands~ :: boolean, ~true~. Whether the priority commands work. With ~false~ they refuse (~Priority commands are disabled~), and ~S-<up>~ and ~S-<down>~ on a headline do not change its priority. (~org-priority-enable-commands~)
- ~org_track_ordered_property_with_tag~ :: boolean, string, ~false~. A tag that ~org.ordered.toggle~ (~C-c C-x o~) puts on the headline with the ~ORDERED~ property and takes off without it: ~true~ for ~ORDERED~, or a tag of your own. Only the property orders the subtasks. (~org-track-ordered-property-with-tag~)
- ~org_special_ctrl_k~ :: boolean, ~false~. C-k (~org.kill.line~) on a headline kills the text to the tags, and the tags when the cursor is past the title; at the start of the line, the whole line. With ~false~ the key keeps the editor's own meaning. (~org-special-ctrl-k~)
- ~org_list_allow_alphabetical~ :: boolean, ~false~. Whether a letter may stand for the number of an ordered item (~a.~, ~B)~). A list of more than 26 items is numbered. (~org-list-allow-alphabetical~)
- ~org_plain_list_ordered_item_terminator~ :: true, ".", ")", ~true~. What ends the number of an ordered item: ~"."~, ~")"~, or ~true~ for either. (~org-plain-list-ordered-item-terminator~)
- ~org_list_two_spaces_after_bullet_regexp~ :: false, string, ~false~. An Emacs regexp: the bullets it matches get two spaces after them when Org writes them (a new item, a bullet changed, a list repaired). (~org-list-two-spaces-after-bullet-regexp~)
- ~org_list_demote_modify_bullet~ :: object, ~{  }~. By bullet (~-~, ~+~, ~*~, ~1.~, ~1)~), the bullet an item gets when it is indented: ~{ "+": "-", "-": "+" }~. (~org-list-demote-modify-bullet~)
- ~org_list_indent_offset~ :: integer, ~0~. How many more columns sub-items are indented, past their parent's bullet. (~org-list-indent-offset~)

* Commands
:PROPERTIES:
:CUSTOM_ID: commands
:END:

Commands run through ~workspace/executeCommand~. The one argument says where
the cursor is, in a document the server knows:

#+begin_src json
{
  "command": "org.todo.next",
  "arguments": [{ "textDocument": { "uri": "file:///home/me/org/work.org" }, "position": { "line": 3, "character": 0 } }]
}
#+end_src

This is ~TextDocumentPositionParams~, with one optional field more: ~count~, a
number the user typed before the key (Emacs's prefix argument, Vim's
count). The commands that move something by steps take it as the number of
steps; the others ignore it. Commands that open a view work without the
argument.

~range~, the selection the command was run on, is Emacs's active region,
with ~position~ at one of its ends (the point) and the mark at the other.
The commands marked ~"region": true~ in the manifest act on it as Org does:
~org-do-promote~ and ~org-do-demote~ on the headlines in it, items outdented
and indented, lines turned into headings or items (~org-toggle-heading~,
~org-toggle-item~), checkboxes toggled (~org-toggle-checkbox~), lines made a
table (~org-table-convert-region~, ~C-c |~), the region moved (~org-metaup~,
~org-metadown~), wrapped in a block, a drawer or emphasis markers. These run
in the server's Emacs (see [[#emacs][Emacs]] below). The server itself refiles the
subtrees selected together (/Refile region to/; /The region is not a
(sequence of) subtree(s)/ otherwise; with ~org_log_refile~, Org's time note
in the last headline it set one up for), stores a link whose search is the
text selected (~org-link-precise-link-target~, no description), and inserts
a link with the text selected as its description, in its place. An empty
range is no selection. Code actions requested over a selection carry it in
their commands, unless it is a single character (Helix's cursor).

~folded~, for the commands marked ~"folds": true~ in the manifest
(~org.export.dispatch~, whose ~C-v~ exports only what shows), is the
editor's closed folds in the window, ~[[first, last]…]~, each the first and
last line of a fold, from 0. ~clipboard~, for those marked
~"clipboard": true~, is the text of the editor's clipboard.

A command's result may carry ~"message"~: what Emacs says in the echo area
when it is done, for the editor to show the same way (Neovim's messages, VS
Code's notifications): /TODO state changed to DONE/ (from the agenda, where
the entry is out of sight), /TODO state was already TODO/, /Priority of
current item set to B/, /Priority removed/, /Scheduled to <2026-05-22 Fri>/,
/Deadline on <…>/, /Timestamp updated/, /Refile to "Projects" in file
/home/me/org/work.org: done/, /Switched to day view/, /Capture process
aborted and target buffer cleaned up/.

A command that runs as a key is typed returns its edit instead of sending
it: ~org.return~ answers ~{ "edits": [TextEdit…], "cursor": Position }~, and
the editor applies the edits to the document at hand and puts the cursor
there before the next key is handled. (A ~workspace/applyEdit~ from the
server, and a cursor moved after it, would race with what is typed next.)
~org.meta.return~ and its neighbours answer the same way. With
~"apply": true~ in the context the server applies the edit itself and moves
the cursor with ~window/showDocument~; the code actions of ~command_actions~
run them so. With ~"below": true~, ~org.meta.return~ and its neighbours put
the new heading, item or table row below the cursor's line, as
nvim-orgmode's ~<Leader><CR>~ does: never above it and splitting nothing, as
Emacs does from the end of the line with ~org-M-RET-may-split-line~ nil (in
a table, ~org-table-insert-row~ with its argument).

A command that cannot run answers with error code -32803 (~RequestFailed~)
and a message meant for the user, such as /No agenda is open/. When the
command means nothing at the cursor (a timestamp key off a timestamp, a
headline command before the first headline), the error's ~data~ is
~{ "notApplicable": true }~. An editor that bound the command to a key with
a meaning of its own (see ~native~ in [[#the-manifest][the manifest]]) then lets the key do
that instead: Vim's ~<C-a>~ on a timestamp changes the date and elsewhere
increments a number.

** How they work

*TODO state changes* do what Org's ~org-todo~ does. The cycle runs through
"no keyword" between the last and first states. The tags of the headline
return to their column, and statistics cookies (~[1/3]~, ~[33%]~) in the
parent headline are recounted. ~CLOSED:~ and state notes are written as
~org_log_done~ and the keywords ask; where Org would prompt for the text of a
note, the note is written without text. An entry with a repeater that is
marked done moves to its next date and is open again, with ~LAST_REPEAT~ and
a state note recorded.

The entry is the innermost headline whose subtree contains the cursor, so
the cursor may be anywhere in the entry's body.

*Priorities* change as ~org-priority-up~ and ~org-priority-down~ do them,
within the file's priorities. Past the highest or lowest the cookie is
removed; the same key pressed again goes on from the other end. "Pressed
again" means the same command on the same entry with no other command in
between; the server cannot see the cursor move, as Emacs can.

*Timestamps* change as ~org-timestamp-up~ and ~org-timestamp-down~ do them
(~S-<up>~, ~S-<down>~ in Emacs): the year, month, day, hour or minute the
cursor is on, the end of a time range together with its start, a repeater
or warning period, or, on a bracket, active against inactive. Minutes move
in steps of ~org_time_stamp_rounding_minutes~ unless a count is given. On a
~CLOCK:~ line the duration is recomputed. In a file, ~org.date.later~ and
~org.date.earlier~ are ~org-timestamp-up-day~ and ~org-timestamp-down-day~. On
an agenda line they are ~org-agenda-date-later~ and ~org-agenda-date-earlier~:
the first step forward takes a date that has passed to today, and a date
range moves as a whole.

*Commands that ask for something.* In the manifest such a command has
~"input": { "kind", "prompt" }~. Run without an answer, it changes nothing
and returns what to ask:

#+begin_src json
{ "input": { "kind": "date", "prompt": "Schedule", "value": "10:00" } }
#+end_src

~value~ is the text the prompt starts with, as Emacs fills it in: the time of
the date being changed (~10:00+1:30~ for a range), or nothing. The editor
asks with its own input box and runs the command again with the answer as
~input~ in the argument:

#+begin_src json
{ "textDocument": { "uri": "…" }, "position": { … }, "input": "fri 10:00" }
#+end_src

A client that does nothing with a command's result (~message_prompts~, on
for a client without org-lsp's editor code) is asked by the server itself.
A choice comes as ~window/showMessageRequest~, a button a choice, and the one
picked runs the command again. LSP has no request for text, so for text and
dates the server says /PROMPT: answer with a rename at the cursor/ (with
~window/showMessage~) and the next rename answers: ~textDocument/prepareRename~
offers ~value~ as the placeholder, and the new name of ~textDocument/rename~ is
the answer, the rename itself an empty edit. Another command first drops the
question, and rename renames again.

An input may say more:

- ~"choices": [{ "key": "t", "label": "TODO" }, …]~ with kind ~key~: the
  answer is one key, as Emacs reads it at its fast selection prompts. The
  prompt is a title (/Select a TODO state/); the editor shows the choices, as
  Emacs shows them in a window of their own. It can list them and read a
  single key press (Neovim) or offer them as a list (VS Code). A space is
  shown as ~SPC~. A TODO keyword comes with its look, to be shown in it as
  ~org-fast-todo-selection~ shows it: ~"highlight"~, the selector of its
  token (~todoKeyword~, ~todoKeyword.done~), and ~"face"~ when
  ~org_todo_keyword_faces~ gives it one, as in ~org-lsp/faces~.
- ~"completions": ["Owner", …]~ with kind ~text~: what may be typed, offered
  as it is typed (Emacs's ~completing-read~); anything else may be typed
  too. An empty answer stands for the default the prompt shows in brackets
  (/Property [Owner]/); with ~"select": true~ there is none, and a
  completion picked with nothing typed is the answer, as completion
  frameworks take it.
- ~"context": { … }~: fields to send back with the answer. A TODO state
  change that records a note (~@~, or ~org-log-done~ set to ~note~) is not
  made until the note's text comes: it asks with kind ~note~ (/Note for state
  change from "TODO" to "WAIT"/) and ~"context": { "state": "WAIT" }~, and the
  answer then sets that state and writes the note under the heading line,
  as ~org-store-log-note~ does. A client that announces
  ~experimental.orgDatePrompt~ (one of this project's integrations) gets a
  note buffer instead, as Emacs's =*Org Note*=: a file named like a capture
  buffer (~CAPTURE-Note.org~), shown with ~window/showDocument~, which starts
  with ~# Insert note for state change from "TODO" to "WAIT".~ and has the
  cursor on its third line. ~org.capture.finish~ there makes the change with
  the text below the comment lines as the note, and ~org.capture.abort~ makes
  it without any (Emacs's ~C-c C-k~); both return ~{ "close": uri }~.

An answer may lead to another question; the editor asks again until the
command asks for nothing more.

A ~date~ answer is read as Org's date prompt reads it (~org-read-date~):
~+2d~, ~fri~, ~2/15~, ~feb 15 3pm~, ~w12~, ~10:00-11:30~, ~++1w~, and so on,
against the date being changed or else today. While it is typed, an editor
can show what it means with ~org.date.preview~, whose argument is the same
plus ~"command"~, the command being answered; it returns
~{ "timestamp": "<2026-05-22 Fri 10:00>" }~, or fails while the answer means
nothing.

*Scheduling* works as ~org-schedule~ and ~org-deadline~ do: the timestamp
goes on the planning line under the headline, which is made when there is
none; a ~CLOSED:~ timestamp is taken out; the repeater of the old date
stays. *Timestamps* work as ~org-timestamp~ does: on a timestamp the command
changes it (keeping its repeater), elsewhere it inserts one
(~org.timestamp.change~ only changes one, active or inactive as it is, and
refuses elsewhere); right after inserting one, the same command adds the
end of a date range (~<…>--<…>~). After a timestamp is inserted, the server
moves the cursor after it with ~window/showDocument~, as Emacs leaves it.

*Code actions.* The commands that apply at the cursor are also offered as
code actions, with the command name as the action's kind. In an Org file
the actions carry their edit (versioned when the client supports
~documentChanges~), except clocking (~org.clock.in~, ~org.clock.out~,
~org.clock.cancel~), which may change another file too and carries its
command; in the agenda they carry the command to run. A client can
therefore also bind a key by requesting code actions with ~context.only~ set
to a kind, which matches hierarchically: ~org~ selects every action.

*Edits to files that are not open.* A command run from the agenda edits the
entry's file with ~workspace/applyEdit~. Editors apply such an edit to a
buffer and leave saving to the user, as Emacs does (unless ~auto_save~). The
agenda follows the edit at once and again when the file is saved.

*Reporting edits at once.* The server builds on the text it was last told
about. A key held down sends the next command before an editor that
batches its ~didChange~ notifications (Neovim waits 150 ms) has reported the
previous edit, and that press is lost. An integration should send the
change as soon as it has applied a ~workspace/applyEdit~.

* Emacs
:PROPERTIES:
:CUSTOM_ID: emacs
:END:

What only Org itself can do, the server has Emacs do: export
(~org.export.dispatch~), Babel's evaluation (~org.babel.execute~ and its
relatives, ~C-c C-c~ on code), footnotes (~org.footnote.action~) and a few
editing commands (~C-c -~ and ~C-c *~ off a table, ~C-c ;~, emphasis, structure
templates, drawers, cloning subtrees, copying down, summing and creating
tables, moving between blocks, timers, the ~%(sexp)~ of capture templates).
It also does what org-lsp's own code leaves to Org: tables whose formulas
are Emacs Lisp, remote references or Calc's units, fractions, symbolic mode
and engineering notation (~org.table.recalculate~ and its relatives), and
tangling a file whose header arguments are Emacs Lisp or whose Noweb
references call a block (~org.babel.tangle~). Emacs is optional; without it
those commands fail with /Cannot start Emacs (…)/ and nothing else changes.

The ~%(…)~ of ~org_agenda_prefix_format~ are Emacs's too. A view is
built at once with what Emacs last made of them (empty the first time),
and the forms on its lines go to Emacs in one request in the background,
each run as
~org-agenda-format-item~ runs it: in the entry's file as the editor has it,
point at the start of the headline (Org leaves it where its search
stopped, on that line or its timestamp), with ~category~, ~extra~, ~time~,
~level~, ~tag~, ~effort~ and ~breadcrumbs~ bound to the line's; a line of
the time grid is in no Org buffer. Once Emacs answers, the view is built
again with what they gave, and the editor told that it changed. A form that signals an error stops Org's agenda; here the
agenda shows, the field empty, and the error is said once. Without Emacs
the fields are empty, and ~org-lsp agenda~ in a terminal leaves them so.

The server starts one ~emacs --batch -Q~ the first time it is needed and
keeps it running, so that Org loads once (a second or so) and each request
costs only its own work. It talks to it over standard input and output
with the Lisp in ~server/org-lsp/src/bridge.el~, from a thread of its own: an
export never holds up the server's other answers. Emacs loads, in this
order, ~emacs_config_file~, then evaluates ~emacs_config~, then loads Org
(~org~, ~ox~, ~ox-publish~): settings made before Org loads are kept
(~org-export-backends~ to add Markdown, a ~load-path~ for another Org), and
the configuration may load Org itself. A request carries the document's
text as the editor has it, unsaved changes and all, in a buffer that
visits the file's path (so that ~#+INCLUDE:~, ~#+SETUPFILE:~ and the output's
name work as they would in Emacs), with the file's safe local variables.
~org-agenda-files~ is the server's agenda files.

Emacs must not read the terminal: a yes-or-no question it asks comes to the
editor as ~window/showMessageRequest~; any other question it would ask fails
the command with /Emacs asked a question org-lsp cannot answer: …/. When
Emacs stops (an error in the configuration), the command fails with what it
last wrote on its standard error, and the next one starts it again.

* The agenda document
:PROPERTIES:
:CUSTOM_ID: the-agenda-document
:END:

The agenda is one document that the server owns, as it is one buffer in
Emacs: a new view replaces the old one. Its language identifier is
~org-agenda~. The server remembers which entry each line stands for, so
semantic tokens, go-to-definition, code actions and commands work on it
like on any document.

A client that announces ~workspace.textDocumentContent~ (LSP 3.18) is shown
~org-agenda:/Org%20Agenda~ and fetches its text with
~workspace/textDocumentContent~. Other clients are shown a file,
~Agenda.org-agenda~ in a temporary directory, which the server rewrites and
removes when it stops. A client without org-lsp's editor code (~org_client~)
gets ~Agenda.org~ instead, which it opens as an Org file with the server
attached: colored, and with every command of the agenda's as a code action
(those with an agenda key in the manifest, and those that work on an agenda
line), the line's entry's first; not follow mode, column view or going to
the entry in another window, which need the editor's code.

Opening a view goes like this:

1. The client runs ~org.agenda.list~.
2. The server sends ~window/showDocument~ with the agenda's URI and, as the
   selection, the line of today's date.
3. The client opens the document, which makes it fetch the text.

When the view changes while the client has it open:

1. The server sends ~workspace/textDocumentContent/refresh~.
2. The client fetches the text again and, since the document is open,
   reports the change with ~textDocument/didChange~.
3. If the cursor is to move (the view went to another week, say), the
   server sends ~window/showDocument~ with the new line only now, when the
   client's copy matches. Sent earlier, the line number would be applied to
   the old text.

For step 3 the client must sync the agenda document like any other:
~didOpen~ when it shows it, ~didChange~ when it replaces the text, ~didClose~
when it closes it. After ~didClose~ the server stops rebuilding the view.

*Changed lines stay where they are.* As in Emacs, a change made from the
agenda does not move the entry's lines: they show the new state, priority
or tags where they are (~org-agenda-change-all-lines~), a new date at their
end, such as ~=> <2026-05-23 Sat>~ or ~S => Scheduled to <2026-05-23 Sat>~
(~org-agenda-show-new-time~), and the cursor stays on its line, so that the
next press of the key reaches the same entry. A repeating entry marked done
shows the state it reached on today's line until the agenda is built again
(~org-agenda-headline-snapshot-before-repeat~). The agenda is built anew
with ~r~ (~org.agenda.redo~), another view, a change typed in a file, or a
change that adds or removes entries. The new date fills the line up to the
width the client reported with ~org-lsp/agendaWidth~ (80 columns without
it), less the column a terminal keeps.

*Lines of a view the client still shows.* A key pressed before the client
has fetched the new text names a line of the old one. The server keeps the
old view until the client's copy has changed, and resolves the line against
it.

Emacs shows a calendar while it asks for a date, and the server does the
same for a client that announces ~experimental.orgDatePrompt: true~ in its
capabilities (and supports ~workspace/textDocumentContent~ and
~window/showDocument~). The prompt is a second document of the agenda's
scheme, ~org-agenda:/Org%20Date~ with the language ~org-date~, as the
manifest's ~datePrompt~ names it. A client that cannot fetch documents sets
the options ~date_prompt~ and ~view_changed~ instead (the Vim plugin): the
prompt is then a read-only file, ~Date.org-date~ beside the agenda's file,
written anew with ~org-lsp/viewChanged~ after each change.

#+begin_example
          April 2026                May 2026                June 2026
     Su Mo Tu We Th Fr Sa     Su Mo Tu We Th Fr Sa     Su Mo Tu We Th Fr Sa
               1  2  3  4                     1  2         1  2  3  4  5  6
      …

SCHEDULED Date+time [2026-05-20]: 10:00    => <2026-05-20 Wed 10:00>
#+end_example

The three months are drawn as Emacs's calendar draws them, the weeks starting
on the day ~calendar_week_start_day~ says (Sunday unless set); the last line is
Emacs's minibuffer: the prompt, what was typed, and what that means. The
selected day has the ~calendarSelected~ token, and the server puts the cursor
on it.

1. A command that asks for a date (~org.schedule~ …) opens the prompt with
   ~window/showDocument~ and returns nothing. The client shows it as it likes
   (Neovim: a window at the bottom, VS Code: beside the file).
2. Its keys are the commands' keys ~in~ the ~calendar~ scope: they move the
   selected day (from the day under the cursor), take the day at the cursor
   (~org.calendar.select~: what was typed and that day), ask for the answer
   (~org.calendar.type~, which returns ~{ "input": … }~ like any command; that
   input box is the minibuffer), or give up (~org.calendar.cancel~). While
   the answer is typed, ~org.date.preview~ also shows it in the minibuffer
   line. ~org.calendar.time~ picks a time, which Emacs's calendar cannot: a
   ~Time: 10:00~ line appears above the minibuffer, and until
   ~org.calendar.time~ again, the day commands choose the hour (earlier) or
   the minutes (later) and the week commands move it (earlier up, later
   down; the minutes by ~org_time_stamp_rounding_minutes~, to a multiple of
   it first, as ~org-timestamp-change~ moves them). The time takes the
   place of a typed one, and stays when the keys go back to days.
3. Answered or picked, the command runs with the answer and the day moved
   to (if it moved), as Emacs reads its prompt; the result is
   ~{ "close": "org-agenda:/Org%20Date" }~, and the client closes that
   document. Cancelling returns the same.

When the selected day moves, the server sends
~workspace/textDocumentContent/refresh~, and once the client shows the new
text, ~window/showDocument~ with the cursor on the day, as for the agenda.
Other clients keep the plain input box.

* Semantic tokens
:PROPERTIES:
:CUSTOM_ID: semantic-tokens
:END:

Tokens never overlap and never span lines. Nested markup is flattened into
modifiers: in =*bold /both/*= the inner text carries ~bold~ and ~italic~.
Emphasis markers are part of the token they delimit. The manifest has the
full legend with descriptions; this is an overview.

For a client without org-lsp's editor code (~org_client~), the server keeps
to the token types and modifiers of the LSP specification, which editors and
their color schemes color without being told. Org's tokens become the
standard ones whose colors come closest to Emacs's faces:

| Org                                                  | Standard                                                      |
|------------------------------------------------------+---------------------------------------------------------------|
| headline and stars, levels 1 to 8 (~outline-1~ …)    | ~function~, ~property~, ~keyword~, ~comment~, ~type~, ~enumMember~, ~macro~, ~string~ |
| TODO keyword, planning keyword                       | ~keyword~                                                     |
| done keyword                                         | ~string~                                                      |
| priority, statistics cookie                          | ~number~                                                      |
| tag                                                  | ~decorator~                                                   |
| timestamp; inactive                                  | ~enumMember~; ~comment~                                       |
| ~#+KEY:~, block lines, comment, hidden text, archived | ~comment~                                                     |
| drawer, LaTeX, entity, macro                         | ~macro~                                                       |
| property key                                         | ~property~                                                    |
| bullet, checkbox, table delimiter                    | ~operator~                                                    |
| link, target                                         | ~namespace~                                                   |
| code, verbatim                                       | ~string~                                                      |
| footnote                                             | ~parameter~                                                   |
| struck-through text                                  | ~variable~ with ~deprecated~                                  |

In the agenda: the title ~namespace~, dates ~function~ (today ~keyword~, a
weekend ~type~), scheduled entries ~string~ (from earlier days ~number~),
deadlines ~enumMember~ (today or past ~keyword~), done entries, the time
grid and dimmed tasks ~comment~. Bold, italic, underlined text and a habit's
graph have no standard kind and get no token.

Keywords, priorities, tags and links inside an agenda line have the types
above. The rest of a line has one of these, which follow Org's agenda
faces:

| Type              | Covers                          | Modifiers                                               |
|-------------------+---------------------------------+---------------------------------------------------------|
| ~agendaStructure~ | The title line of a view        |                                                         |
| ~agendaDate~      | A date line                     | ~today~, ~weekend~                                      |
| ~agendaScheduled~ | A scheduled entry               | ~today~; ~past~ when scheduled before today             |
| ~agendaDeadline~  | An entry with a deadline        | ~imminent~ when due or overdue, ~distant~ when far away |
| ~agendaEvent~     | An entry with a plain timestamp | ~range~ inside a date range                             |
| ~agendaDone~      | An entry that is done           |                                                         |

** Modifiers

- ~level1~ … ~level8~ :: On ~headline~ and ~stars~. Levels above eight wrap
  around.
- ~done~ :: On ~todoKeyword~; on the rest of a done headline (~org-headline-done~),
  in place of its level; on a complete ~cookie~ (~[2/2]~, ~[100%]~).
- ~inactive~ :: On ~timestamp~.
- ~checked~, ~partial~ :: On ~checkbox~.
- ~bold~, ~italic~, ~underline~, ~strikethrough~ :: On ~text~ and
  ~headline~.
- ~today~, ~weekend~, ~past~, ~imminent~, ~distant~, ~range~, ~current~ ::
  On the
  agenda types, as listed above.
- ~archived~ :: On a headline with ~:ARCHIVE:~ in it, all of it but the
  stars
  (~org-archived~, a shadow over its other colors).
- ~hidden~ :: On text Org hides: the brackets of a link, and its target when
  it has a description (~org_link_descriptive~); emphasis markers
  (~org_hide_emphasis_markers~). It comes as tokens of its own, so an editor
  that can conceal text conceals the tokens with this modifier: Neovim with
  extmarks in the semantic tokens' namespace, VS Code with decorations.

* Writing an editor integration

An integration should stay free of Org logic. Its whole job:

1. Start ~org-lsp~ for ~org~ files, and on demand for the agenda.
2. Apply the manifest: link the tokens to the editor's highlight names and
   bind the keys of its preset to the commands.
3. Run commands with the cursor position as their argument.
4. Show the agenda document and keep it in sync, as described above;
   likewise the date prompt document, if it announces it, and close it when
   a command returns ~close~.
5. Open and close folds; the server only says where they are.

~lua/org-lsp/~ does this at run time. ~editors/vscode/~ cannot, because VS Code
wants commands, keys and token colors declared in ~package.json~: there
~scripts/generate.mjs~ writes them from ~org-lsp manifest~.

Without an integration, an editor still gets what its LSP client supports
on its own: highlighting, folding, the outline, and TODO changes as code
actions. Commands need the cursor position as an argument, which generic
clients do not send, and the agenda needs ~window/showDocument~.
