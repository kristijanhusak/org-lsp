#+title: Developing org-lsp
#+options: ^:{} toc:nil

How org-lsp is built, checked and published: the rules the work
follows, the checks each change goes through, how a version is released,
and the decisions taken on the way. What Emacs
Org does that org-lsp does not yet is in [[file:parity.org][parity.org]]; what an editor
integration has to do, in [[file:protocol.org][protocol.org]].

* Goal and rules
:PROPERTIES:
:CUSTOM_ID: goal-and-rules
:END:

Org mode in any editor with an LSP client (Neovim, VS Code, Vim, Helix,
others), as close to Emacs Org mode as it can get.

- /Server in Rust, parser written from scratch./ No tree-sitter.
- /LSP only./ No second server and no protocol of its own. Where LSP has
  no fitting request, the feature waits or uses what LSP has (commands
  with arguments, server-owned documents, semantic tokens).
- /As much as possible in the server./ Editors get glue: a loop over
  tables the server announces (commands, keys, highlight links), not
  logic. A new feature should need no new editor code.
- /Emacs is the reference./ Org logic is ported from the Emacs sources
  (Org 9.8.10) and compared with Emacs by committed reference cases and
  by differential fuzzing. A deliberate difference is written down. The
  options are part of it: each of Org's options is in
  ~scripts/org-options.json~, with what org-lsp does with it (a setting,
  missing, read by Emacs, and so on), and [[file:parity.org::#options][parity.org]] lists those
  missing. What Emacs says of those it reads (their docstrings, defaults
  and types, for [[file:emacs-options.org][emacs-options.org]] and the schema of ~emacs_options~)
  is in ~scripts/emacs-options.json~, which
  ~scripts/emacs_options_reference.py~ records again when an option
  changes status.
- /One repository/, Neovim files at the root (~plugin/~, ~lua/~), other
  editors under ~editors/~.
- /Small changes./ Each is one pull request, with its tests, its docs and
  the parity table, merged by squashing once the checks pass.

:CUSTOM_ID: how-the-work-is-checked

* End-to-end scenarios
:PROPERTIES:
:CUSTOM_ID: end-to-end-scenarios
:END:

What a user does in any editor, written once: ~tests/e2e/scenarios/NAME.json~,
each a few files, the options the server starts with and the steps taken.
The server's runner (~server/org-lsp/tests/e2e_scenarios.rs~) takes them as
an editor with org-lsp's plugin would, over LSP, and is the reference: what
it sees is in ~tests/e2e/expected/NAME.txt~, written again with
~ORG_LSP_UPDATE_E2E=1~ (~ORG_LSP_E2E=NAME~ runs only the scenarios whose name
has ~NAME~ in it). Each editor has an adapter that presses that editor's keys
for the same steps and must see the same; Neovim's is
~tests/nvim/scenarios.lua~ (~scripts/test-nvim.sh~ runs it), Vim's
~editors/vim/test/scenarios.vim~, which ~editors/vim/test/run.sh~ runs with
each LSP client after the plugin's own tests, each scenario in a Vim of its
own, four at a time:

#+begin_src sh
CLIENTS=~/vim-clients editors/vim/test/run.sh                  # the tests, then the scenarios
ORG_LSP_VIM_TESTS=scenarios ORG_LSP_E2E=capture \
  CLIENTS=~/vim-clients editors/vim/test/run.sh coc            # one scenario, one client
#+end_src

~ORG_LSP_VIM_TESTS~ is ~cases~ or ~scenarios~ for only those,
~ORG_LSP_E2E_JOBS~ how many Vims run at once. Each scenario prints one line,
with the step that failed and what it saw; a step a client cannot take as
the others do is skipped, with the reason, from ~s:skips~ in
~scenarios.vim~ (coc.nvim shows the documents the server asks for itself).

A scenario has:

- ~files~ :: file names and their text, a string or a list of lines; or
  ~files_from~, a directory under ~tests/~ whose ~.org~ and ~.org_archive~
  files it takes (the recorded agenda cases), and ~files~ on top.
- ~clock~ :: the server's clock, ~{ "today": "2026-05-18", "now": "10:30" }~
  unless it says otherwise.
- ~options~ :: the server's options, over those every scenario has: the
  clock, ~org_agenda_files~, ~org_directory~ and ~org_default_notes_file~ in
  the scenario's directory. ~$DIR~ in a string is that directory.
- ~emacs~ :: ~true~ for a scenario that needs Emacs (column view): it is
  skipped without it, unless ~ORG_LSP_REQUIRE_EMACS~ is set.
- ~steps~ :: what is done, in turn. A step may open a file (~"open":
  "work.org"~), go back to a buffer that is open (~"focus": "agenda"~), close
  the agenda (~"close": true~), put the cursor on a line (~"line": 3~, from 1)
  or where some text is (~"at": "Call the client"~, ~"column"~ further on),
  type text where the cursor is (~"type": "Call mom"~, as in insert mode),
  and run a command by its name in the manifest (~"command":
  "org.agenda.later"~), with a ~count~, ~"below": true~ for the keys of
  modal editors that add below the cursor's line (~<Leader><CR>~), and the
  ~answers~ to what it asks, in turn: a key, text, ~{ "choice": "Projects" }~
  for a choice by its label, or a date, typed in the date prompt
  (~org.calendar.type~). ~"wait": "columns"~ waits for column view, which
  Emacs works out. The adapter presses the command's key in the editor (the
  first; it checks that the others are set too), where the cursor is: the
  agenda, the date prompt, a capture buffer, an Org file.
- ~expect~ :: after the step, what to look at: ~agenda~ (the agenda's text),
  ~file:NAME~ (a file, as the editor has it), ~buffer~ (the current
  buffer's name and text), ~cursor~ (its name, the cursor's line and that
  line's text), ~messages~ (what was said since they were last looked at),
  ~columns~ (column view). ~"emacs": "agenda/NAME/expected-N.txt"~ on a
  step also checks the agenda against that view, recorded from Emacs.

~scenarios_cover_the_agenda_calendar_and_capture~ fails when a command with
a key in the agenda, the date prompt or a capture buffer is in no scenario,
unless ~tests/e2e/exceptions.json~ names it under ~commands~ with the reason.
An adapter fails on a command that has no key in its editor, unless
~editors.EDITOR~ there says why; it then runs the command as from the
editor's command list. ~snapshots.EDITOR~ names, as ~NAME STEP KIND~, what
an editor shows otherwise on purpose, and why; ~steps.EDITOR~, as ~NAME
STEP~, the steps an editor cannot take, and ~scenarios.EDITOR~ the
scenarios it cannot run at all, each with the reason.

VS Code's adapter is ~editors/vscode/test/scenarios.test.cjs~, run by
~npm test~ after the extension's tests (~npm test -- scenarios~ for the
scenarios only, ~npm test -- scenarios vim~ for one preset;
~ORG_LSP_E2E=NAME~ as above). Each scenario runs in a VS Code of its own,
with each preset of ~org-lsp.keys~: ~emacs~ (~editors.vscode~ in the
exceptions) and ~vim~ (~editors.vscode-vim~, which leaves the keys of Vim's
normal mode in Org files to VSCodeVim). The adapter finds the key
~package.json~ binds to the step's command where the cursor is, by its
~when~ clause, and presses it in VS Code's window with ~xdotool~, so that
VS Code's own key dispatch runs; it checks that the key ran that command.
VS Code gives a key no count: for a step with a count, ~test/run.mjs~
binds a key of the user's with ~"args": { "count": N }~, as
[[file:keys/vscode.org::#changing-them][a user does]]. A step ~below~ puts
the cursor at the end of its line first, as ~C-e M-RET~ in Emacs. What is
asked is answered by stubs of VS Code's quick pick and input box. It needs
~xdotool~ and a display of its own, ~xvfb-run -a npm test~: the keys go to
the window that has the focus.

Helix's adapter is ~editors/helix/test/run.py~: each scenario in a Helix
of its own in a tmux session, with [[file:../editors/helix/languages.toml][editors/helix/languages.toml]] pointing
at the debug build and the scenario's options as its ~config~. It does
what a Helix user does, every key typed in Helix's terminal through tmux:
picks the command's code action in the menu (~Space a~, then ~C-n~ and
~RET~), in Org files, the agenda and capture buffers, follows a link with
~gd~, saves with ~:write-all~ (the agenda's save, which Helix does not
do for a server), picks the answer to a choice from the code actions,
where it comes first, answers what the server asks for as text with a
rename (~Space r~, the answer typed), goes to a line with ~:goto~ or a
search, opens a file with ~:open~ and goes back to the agenda from the
buffer picker (~Space b~). A code action takes no count: a step with one
picks the action that many times, or once where Org gives the count no
meaning (~COMMAND count~ under ~editors.helix~). A step that adds below the
cursor's line goes past its end first (~gl l~), as ~C-e M-RET~ does, and
after moving a subtree, whose code action leaves the cursor where it was
in the text, the adapter goes after the subtree with a search. What Helix
cannot do (follow mode, the entry in another window, a count Org reads
as more than a repeat) is under ~steps.helix~, whose steps still put the
cursor where they say for the steps after them. It reads the buffers'
text from what Helix tells the server (~didOpen~ and ~didChange~ in its
log), the cursor from the status line and the messages from the log too.
The date prompt and column view are not there (~scenarios.helix~). ~HX~ is the ~hx~ to run (~HELIX_RUNTIME~ its
~runtime~ directory, by default the one beside it; ~ORG_LSP_HX_KEEP~ keeps
each scenario's directory and Helix's log); ~scripts/test-all.sh~ runs it
when ~HX~ is set:

#+begin_src sh
HX=~/helix/hx editors/helix/test/run.py
HX=~/helix/hx ORG_LSP_E2E=org-editing editors/helix/test/run.py
#+end_src

Zed's adapter is ~editors/zed/test/run.py~, which ~scripts/test-all.sh~
runs when ~ZED~ names Zed's command line (~bin/zed~):

#+begin_src sh
ZED=~/zed.app/bin/zed ZED_ORG_GRAMMAR=~/org.wasm editors/zed/test/run.py
ZED=… ZED_ORG_GRAMMAR=… ORG_LSP_E2E=capture editors/zed/test/run.py   # one scenario
#+end_src

Each scenario runs in a Zed of its own, on an X display of its own
(~Xvfb~), with a home directory of its own: the extension installed as
~scripts/install.sh zed~ installs it, built with ~cargo build --release
--target wasm32-wasip2~ in ~editors/zed~, the Org grammar Zed would build
(~ZED_ORG_GRAMMAR~, an ~org.wasm~; or ~ZED_TREE_SITTER_ORG~, a checkout of
tree-sitter-org, and ~WASI_SDK~ to build it), and the tasks and the keymap
of [[file:keys/zed.org::#keys-through-tasks][keys through tasks]].
Every step is typed in Zed's window with ~xdotool~, as a user types it.
The adapter presses the key ~keymap.json~ binds to the step's command (a
task, which reaches the server through its command port, or Zed's own
~workspace::SaveAll~ for the agenda's save, after which the files are
checked on disk); a command with no key in Zed (~editors.zed~ in the
exceptions) runs from the code actions (~ctrl-.~, down to the action,
~RET~). It clicks the buttons of a question with the mouse (Zed's
notifications take no keys), answers typed text with a rename at the
cursor (~F2~, the answer typed), goes to a line with ~ctrl-g~ and opens a
file, or goes back to the agenda, with the file finder (~ctrl-p~, the
file's name typed, ~RET~). A key that takes a count is pressed that many
times, as Zed gives a key none. One key is the adapter's own, bound to
Zed's ~workspace::ClearAllNotifications~: the messages it clears would
cover a question's buttons. Zed opens a file a server's edit
changes when no tab shows it, and takes the focus to what it is asked to
show without it (follow mode): the adapter goes back to where it was, as a
user does. What Zed has open, the text of its buffers and where its cursor
is come from what it tells the server, which ~editors/zed/test/proxy.py~
writes down; the current buffer is the window's title. ~snapshots.zed~ in
the exceptions names what Zed shows otherwise as ~NAME STEP KIND~, and the
steps it cannot take as ~NAME STEP~; ~scenarios.zed~ the scenarios it cannot
take at all (the date prompt, column view). After the scenarios come
checks of Zed's own, written as they are, with what they expect (~CHECKS~
in ~run.py~): ~zed-capture-here~ captures with ~ctrl-c c~ in an Org file,
whose ~%a~ links to the cursor's heading, with the agenda open too. Each
wait has a bound: a
request left with no answer fails the step, and a scenario fails when it
takes more than ~ORG_LSP_ZED_BUDGET~ seconds (600), with the step and what
it waited for. Stopped (~SIGTERM~, ~SIGINT~), the adapter closes its Zeds
and their displays. A failure leaves a screenshot
in ~target/zed-e2e~; ~ORG_LSP_ZED_KEEP=1~ keeps each scenario's directory,
and ~ORG_LSP_ZED_PAUSE=1~ leaves Zed open at a failure, to look at.
Each Zed takes the first free X display from ~ORG_LSP_ZED_DISPLAY~ (90)
up.

* Highlighting
:PROPERTIES:
:CUSTOM_ID: highlighting
:END:

~tests/e2e/highlight~ is a sample of every construct the server colours:
~sample.org~, an agenda file (~agenda.org~: scheduled, deadlines near and
far, an event, a range, a done entry, a blocked one, a running clock, a
habit), a journal and daily notes for the date prompt, and the options
they need (~options.json~, ~$DIR~ the directory it is copied to). Each
check copies it and starts the server with those options.

- ~server/org-lsp/tests/highlight.rs~ (~cargo test~): the tokens of the
  file, the week's agenda, the TODO list and the date prompt at the places
  its table ~EXPECTED~ names, which has every token type and modifier of
  the legend; and a token for each look of the manifest's ~highlights~.
  ~ORG_LSP_HIGHLIGHT_DUMP=1~ prints every token.
- Neovim, ~tests/nvim/highlight.lua~ (~scripts/test-nvim.sh~): for each
  look, the token's group drawn at a token it applies to, linked to the
  group the manifest names, defined in the default colorscheme, and its
  colors what shows where no more specific look applies; what Org hides
  concealed.
- Vim, ~editors/vim/test/highlight.vim~ (~editors/vim/test/run.sh~, each

* Publishing
:PROPERTIES:
:CUSTOM_ID: publishing
:END:

org-lsp has one version, written in every place that needs it: the
server's workspace (~Cargo.toml~, ~Cargo.lock~), the VS Code extension
(~package.json~, ~package-lock.json~), the Zed extension
(~extension.toml~, its ~Cargo.toml~ and ~Cargo.lock~) and the Sublime Text
package (~VERSION~ in ~plugin.py~). ~scripts/version.sh 0.2.0~ sets it in
all of them; ~scripts/version.sh~ alone prints it, and fails when they
disagree, which ~scripts/check.sh~ checks.

A release is a version tag. Set the version, merge that change as any
other, then tag the commit on main and push the tag:

#+begin_src sh
scripts/version.sh 0.2.0
# … pull request, merged …
git fetch origin
git tag v0.2.0 origin/main
git push origin v0.2.0
#+end_src

The Release workflow (~.github/workflows/release.yml~) fails when the tag
is not ~v~ and the version, builds everything, makes the GitHub release,
then publishes it: each of these jobs is skipped while its secret is not
set, and the nightly build (the workflow run by hand on main) publishes
none of them.

- ~vscode-marketplace~ (secret ~VSCE_PAT~) :: the VS Code packages, one a
  platform, on the VS Code Marketplace;
- ~open-vsx~ (~OVSX_PAT~) :: the same packages on Open VSX;
- ~zed-registry~ (~ZED_EXTENSIONS_TOKEN~) :: a pull request to Zed's
  extension registry for the new version;
- ~sublime-mirror~ (~SUBLIME_MIRROR_TOKEN~) :: ~editors/sublime/LSP-org~
  and the tag to ~kristijanhusak/LSP-org~, which Package Control reads.

The VS Code packages have the server inside. The Zed extension and the
Sublime Text package download the server of their own release (~v0.2.0~
for version 0.2.0); those of the nightly build, the nightly server. The
VS Code extension is marked as a preview (~"preview": true~ in
~package.json~) until that line goes.

The secrets go in the repository's settings, under /Secrets and
variables › Actions/
([[https://github.com/kristijanhusak/org-lsp/settings/secrets/actions]]).

** Zed
:PROPERTIES:
:CUSTOM_ID: zed
:END:

The registry is the repository ~zed-industries/extensions~, where each
extension is a submodule and an entry of ~extensions.toml~
([[https://zed.dev/docs/extensions/publishing/publishing-guide][Publishing Guide]]). The job updates an extension that is there already,
so the first version goes in by hand, once its tag is released:

- [ ] Fork [[https://github.com/zed-industries/extensions]] to
  ~kristijanhusak/extensions~ (a personal account, so that Zed's staff can
  push to the pull request), and clone the fork:
  #+begin_src sh
  git clone https://github.com/kristijanhusak/extensions
  cd extensions
  git submodule init
  git submodule update
  #+end_src
- [ ] Add org-lsp as a submodule, at the released tag (its commit is on
  main, as the registry wants):
  #+begin_src sh
  git submodule add https://github.com/kristijanhusak/org-lsp.git extensions/org-lsp
  git -C extensions/org-lsp checkout v0.2.0
  git add extensions/org-lsp
  #+end_src
- [ ] Add its entry to ~extensions.toml~; ~version~ is that of
  ~editors/zed/extension.toml~ at the tag:
  #+begin_src toml
  [org-lsp]
  submodule = "extensions/org-lsp"
  path = "editors/zed"
  version = "0.2.0"
  #+end_src
- [ ] ~pnpm sort-extensions~, which sorts ~extensions.toml~ and
  ~.gitmodules~; commit, push, and open the pull request to
  ~zed-industries/extensions~. A pull request adds or updates one
  extension, and is closed after three weeks without an answer to the
  maintainers. The registry has an extension for Org already (~org~,
  from ~hron/zed-org~), and Zed's [[https://zed.dev/docs/extensions/publishing/prerequisites][prerequisites]] ask for no second
  extension that does the same: the pull request should say what org-lsp
  adds (the server).
- [ ] For the versions after it: a classic token of ~kristijanhusak~
  ([[https://github.com/settings/tokens/new]]) with the ~public_repo~ and
  ~workflow~ scopes, as the secret ~ZED_EXTENSIONS_TOKEN~. The job
  ([[https://github.com/huacnlee/zed-extension-action][huacnlee/zed-extension-action]]) pushes the new version to a branch of
  the fork and opens the pull request.

The extension's licence is ~editors/zed/LICENSE~ (the GNU GPL, version
3), which Zed accepts and wants at the extension's root.

** Package Control
:PROPERTIES:
:CUSTOM_ID: package-control
:END:

Package Control installs a package from the root of a repository of its
own, at its version tags (~v0.2.0~ is read as 0.2.0), so
~editors/sublime/LSP-org~ is copied to ~kristijanhusak/LSP-org~ with each

not in Package Control's default channel ([[https://github.com/wbond/package_control_channel][wbond/package_control_channel]]
says so).

  ([[https://github.com/new]]; no README, licence or ~.gitignore~: the job
  pushes the package's), with a description, such as /Org mode in Sublime

- [ ] A fine-grained token
  ([[https://github.com/settings/personal-access-tokens/new]]): /Only select
  repositories/, ~kristijanhusak/LSP-org~; /Repository permissions ›
  Contents/: /Read and write/. It is the secret ~SUBLIME_MIRROR_TOKEN~.
- [ ] Once a version's tag has been copied there: fork
  [[https://github.com/sublimelsp/repository]], add the package to the
  ~packages~ of ~repository.json~, in alphabetical order, and open the
  pull request:
  #+begin_src json
  {
    "details": "https://github.com/kristijanhusak/LSP-org",
    "name": "LSP-org",
    "labels": ["language syntax", "lsp", "org"],
    "releases": [
      {
        "sublime_text": ">=4132",
        "tags": true
      }
    ]
  }
  #+end_src
  4132 is the oldest build of Sublime Text that the LSP package's
  releases are for.

* Decisions
:PROPERTIES:
:CUSTOM_ID: decisions
:END:

1. /Typed input over LSP only./ Decided: the editor's input box, and
   a calendar for dates; in an editor without org-lsp's code, a rename at
   the cursor (see [[file:any-editor.org][any-editor.org]]).
2. /Licence./ Decided: the GNU GPL, version 3 or later (~LICENSE~), as
   Org mode's: ~org-core~ ports Org's own code, which makes it a work
   based on Org. (MIT before.)
3. /Saving after edits from the agenda./ Decided: saved by default
   (~auto_save~), unlike Emacs: the files a command changes other than the
   one it was run in (from the agenda, a capture or refile target) are
   saved once the editor has applied the change (the ~org-lsp/save~
   notification). Off, they stay unsaved, as in Emacs, and
   ~org.agenda.save~ (~org-save-all-org-buffers~, ~s~ in the agenda) saves
   them.
4. /Vim./ Decided: one Vimscript plugin with the logic the Neovim plugin
   has (manifest, keys, the agenda and date prompt buffers, closing them),
   on top of whichever LSP client is installed. Generic LSP (highlighting
   where the client supports semantic tokens, outline, folding, code
   actions) needs nothing. Running commands with the cursor position and
   answering the server's requests differ per client (vim-lsp,
   yegappan/lsp, coc.nvim, ALE), so the plugin has a small adapter per
   client: send a request, receive one. Keep as much as possible in the
   shared code, and write adapters for the most used clients: yegappan/lsp
   (Vim 9's own), vim-lsp, coc.nvim and ALE. Clients without server-owned
   documents get the agenda as a file (the server already writes one) and
   the plain input box instead of the calendar.
5. /A small priority cookie before ~COMMENT~./ Decided: ~* [#a] COMMENT x~
   is not a commented headline, in every view. Emacs works out
   ~:commentedp~ once, when it is first asked, and keeps it: the agenda
   and the TODO list ask with ~case-fold-search~ nil, where ~[#a]~ is no
   cookie, a tags match with it on, where it is one and the headline is
   commented. What a view shows then depends on which view ran first.
   org-lsp reads the cookie with case, as the agenda, ~org-get-heading~
   and ~org-element-context~ do, and ~scripts/agenda_reference.py~ asks
   Emacs that way before any view, so the recorded cases agree.
6. /org-protocol./ Decided: every server listens for ~org-protocol~ URLs
   on a local socket of its own, beside LSP, as the command port does for
   Zed's keys: a URL comes from outside any editor, and LSP has no way in
   for it. ~org-lsp protocol URL~ finds the server the user worked in
   last through the state directory, and a server the editor of
   ~org_protocol_editor~ starts takes what was left for it
   ([[file:protocol.org::#org-protocol][protocol.org]]). A Unix socket in a directory only the user may
   enter (a loopback port with a token on Windows); nothing from a URL is
   run.
